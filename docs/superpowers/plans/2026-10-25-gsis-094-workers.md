# GSiS v0.9.4 Worker authority implementation plan

> For agentic workers: use Superpowers subagent-driven development. The user has authorised implementation, review, commit and full-suite packaging. Do not deploy to production or change subscriptions.

**Goal:** deliver the accepted v0.9.4 scope with Roster and Deploy operational authority in Workers/D1, compressed private R2 timetable packages, fast peer state, a repaired Venues source flow and complete handover documentation.

**Architecture:** reuse the existing pure domain models and identity validation. Put durable records, revisions, receipts, audit and job intent in D1; keep large immutable timetable objects in R2. Keep explicit adapters for Google integrations. Cutover disables legacy writers and preserves one authority.

**Tech stack:** browser JavaScript/IndexedDB, Cloudflare Pages Workers, D1, R2, Queues/Cron, Apps Script Google adapters, existing Node/Python build and regression tools.

**Spec:** docs/v094/ACCEPTED_SCOPE.md and CHANGELOG_v0.9.4.md. Preserve all accepted rules and prior release behavior unless the spec changes it.

## Constraints

1. No secrets or real capability tokens in source or release archives.
2. No production changes or messages during testing. Template submission already occurred; verify its status before activation.
3. Preserve human allocation choices, peer approval semantics, role checks, capability expiry, audit identity and idempotent retries.
4. Absence capture must not wait for allocation, notification delivery or package compression.
5. The final package must include every viewport and backend plus install, migration, rollback, maintenance and API documentation.
6. A stored queue receipt is not a completed operational save. A template approval is not sender activation. Documentation must use exact states.

## Review focus

1. Concurrent writes and retries cannot lose absence reports or overwrite newer human assignments.
2. Slow R2 jobs and date rollover cannot advertise stale content as current.
3. Public peer/acknowledgement routes cannot bypass capability checks or mutate legacy state after cutover.
4. Partial Deploy publication and failed Google handoffs remain recoverable without publishing a draft to downstream readers.
5. Import/cutover/rollback retain record identities, receipts and notification outcomes; no automatic fallback to a second writer.

## Work packages

### 1. D1 storage and migration primitives

Create shared/edge-store.js and SQL migration(s), with tests for real SQLite transactions, optimistic revisions, receipt identity, changed-record writes and replay. Export a small store interface shared by Roster and Deploy. Publish the exact interface to the implementation agents before their integration. No single mutable database blob.

### 2. Roster operational adapter

Create Worker modules around shared/roster*.js. Migrate browser and signed service dispatch, reference/context assembly, baseline and STAPLER persistence, leases, peer/absence state and allocation/publication. Preserve endpoint envelopes and fine-grained conflict tokens. Add migration export/import and legacy writer fence. Own new edge modules; coordinate edits to roster-update/public/_worker.js with the notification adapter.

### 3. Deploy operational adapter

Create Worker modules around shared/planning.js, fields.js, teaching-rules.js, workload.js and relief.js. Preserve bootstrap/delta/receipt/lease/change/publication and published reference contracts. Treat Contacts approval and Layout/catalogue synchronization as durable cross-service workflow. Add migration export/import and legacy writer fence.

### 4. Notification operations

Move claims, preparation, outcomes, webhook/inbox state and private peer/acknowledgement decisions to the Roster D1 authority. Keep actual sends in the existing background Worker, preserve uncertain-send handling and sender-wide rate limiting. Activate the v2 peer template only after approval and verify four body parameters plus URL button index 0. Coordinate with the Roster adapter owner.

### 5. Timetable packages and Venues

Diagnose Venues coverage failure through its current source contract, fix with regression evidence, and connect it to Worker-owned published sources. Keep compressed immutable R2 parts and current manifests, including targeted rebuilds after saves. Preserve verified booking conflict checks and incomplete refresh UX.

### 6. UI and documentation

Make the Roster title a keyboard-accessible padded home target using existing navigation/unsaved guards. Preserve fast peer indicators from committed partial responses. Produce a single maintainer README, exact environment/property ledger, migration/cutover/rollback runbook, API/ownership map, capability and competency guide, and self-contained Archify architecture documentation using available design skills.

### 7. Integrated verification and release

Run relevant new regression tests while implementing, then the complete Node and LORD checks, Apps Script syntax checks and release verification. Review diffs across all viewports, test concurrent saves and archive contents, harmonise all components to 0.9.4, commit, tag and package a complete suite with source recovery. Record actual passing evidence and any environment limitations without claiming a live deployment.
