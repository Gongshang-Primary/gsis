Prepare native timetables on Cloudflare

This build replaces the isolated rehearsal Worker with a timetable-only preparation screen. It uses the D1 database and private R2 bucket you have already tested. No production cutover is included. Google remains authoritative for baseline uploads, Stapler changes, attendance, allocation and notifications.

What the result means

A passing import proves that a particular exported snapshot can be stored and read back consistently. It does not prove the Cloudflare copy remains current after another Google edit. Normal Roster users continue through the existing Google pipeline.

2. Preserve the rehearsal Worker version

  1. Open Cloudflare. Select the same account used in your successful rehearsal.
  2. Click Workers & Pages → gsis-roster-rehearsal → Deployments. Record the currently active version ID and keep your tested I worker.mjs copy, including the live sign-in correction.
  3. Open Settings → Bindings. Check the two bindings above. Keep production bindings and credentials out of this rehearsal Worker.
  4. Open Settings → Variables and Secrets. Check the six existing variables and origin, without a trailing slash.

Your live I report identified a server runtime difference: Google's JWKS fetch must use redirect:'manual' on Workers. O includes that fix in source. The browser's own same-origin fetch retains redirect:'error'. Any redirect from Google's key endpoint is still rejected.

3. Add the preparation tables

  1. Click Storage & databases → D1 SQL Database.
  2. Open gsis-roster-rehearsal-ledger-gsps-20261028-01, then click Console.
  3. Open this package's schema.sql as plain text. Copy the complete contents into the SQL console and click Execute.
  4. Confirm the new preparation tables appear. The script is additive and can be run again. It contains no table reset, data deletion or production migration.

The schema uses a block comment rather than a leading -- line comment, because the dashboard may collapse pasted lines. The original rehearsal_* tables must remain present.

If the schema reports an error

Stop and keep the exact error. Do not delete the existing database, remove its marker or run the old I creation script again. Those actions would destroy the evidence you already verified.

4. Check R2 privacy, then install this Worker

  1. Click Storage & databases → R2 object storage and open the existing rehearsal bucket.
  2. Open Settings. Confirm Public Development URL is disabled and no public custom domain is connected.
  3. Return to Workers & Pages → gsis-roster-rehearsal → Settings → CPU Limits. Set the per-request CPU limit to 10,000 milliseconds (10 seconds) for this bounded paid-plan rehearsal. The supplied Wrangler example uses the same ceiling.
  4. Open Edit code. Replace the Worker module with this package's top-level worker.mjs. Click Deploy. This is the rehearsal Worker, not gsis-roster-notifications, the production Operations Worker or Roster Pages.
  5. Open the same rehearsal origin. Sign in using an allowlisted school account.

This package is a single bundled module, so no extra import files need to be pasted into the dashboard. It has no cron trigger, queue consumer, activation endpoint or message-sending capability. If Cloudflare asks for storage bindings, use the existing names in section 1. A mismatched marker or an extra credential causes a configuration error.

Cloudflare documents the CPU setting under the Worker's Settings. This is a ceiling, not a reservation: actual CPU is what runs. After a native school-scale import, inspect the invocation's CPU and wall time in Observability before deciding this size is suitable. See Cloudflare's limits documentation.

5. Export the Google source without changing it

Install the accompanying O Roster backend and frontend export addition using the main O setup guide. That addition keeps production authority unchanged and adds administrator-only read operations.

  1. Sign in to production Roster with your administrator account.
  2. Open System Health → Prepare timetable migration. The page is /timetable-preparation.html on the Roster origin.
  3. Click Download timetable snapshot. Keep the tab open until every bounded part and the final source check have completed. A changed source should stop the export and ask you to start it again.
  4. Store the downloaded JSON privately. It contains school timetables and staff identities; it is not a public teaching resource.

The export covers Singapore today through 30 days in the future, inclusive: 31 dates. It contains the relevant native baselines and confirmed intended Stapler timetables. An unconfirmed draft is excluded even if it is newer than the confirmed plan. A confirmed suspended plan can exist without a baseline, and a later baseline does not rewrite that intended plan.

Absence records, relief assignments, contacts' private details, notification queues and private notes are excluded. The export does not use pending absence intake as a migration gate.

6. Import and check the snapshot

  1. In the rehearsal timetable preparation page, choose the downloaded JSON bundle, then click Inspect file.
  2. Read the file summary: date window, number of native source parts and source identity.
  3. Click Import and verify snapshot. The page uploads bounded parts separately, verifies their hashes, then requests an atomic D1 commit against the revision it read.
  4. Wait for the readback result. A successful result must show verified R2 content and matching native timetable comparisons, with an imported snapshot revision.
  5. Click Refresh stored status. Confirm that the revision and content hashes agree with the completed import. Choose a date and timetable kind, then click Read compressed copy to inspect a dated working copy.

Native source parts and dated working schedules are compressed independently in private R2. D1 stores the manifest, per-date object pointers, source identity, import receipts and revision history. The Worker verifies bounded gzip decompression and SHA256 before advancing a D1 head. Failed or corrupt R2 objects cannot advance it.

Each native source part is limited to 4 MiB of plain JSON; the complete source snapshot is limited to 64 MiB. Part requests have a 9 MiB bound to allow JSON string escaping. Imports beyond those limits are refused without advancing the stored head. Processing is sequential so the Worker does not retain the entire native snapshot in memory.

Where a baseline supports odd and even weeks, the preparation retains and compares those native projections. Calendar parity is not verified by this export. It must not label an arbitrary odd/even projection as the live dated baseline. Pure confirmed suspended timetables can be checked directly because their intended outcomes are independent of the current baseline.

Retry and conflict behaviour

After an uncertain commit response, click Retry last commit to retry the exact request ID, revision and body. Do not create a new import to guess whether the first one committed. A stale revision requires reloading and reviewing the current snapshot. Re-importing unchanged content reuses immutable R2 objects; it does not overwrite a different object at that key.

If retry information is held only in the open browser tab, reloading loses that local request state. Read the server's latest state before starting another import.

8. What remains before Cloudflare becomes authoritative

No production cutover is performed by this build. A later controlled handover must fence every baseline and Stapler writer, take a final source check and delta, commit the new authority revision, and route all timetable consumers through the correct visibility rules. It must also provide source-change-driven refresh, the Singapore rolling date window, safe pruning and a Google backup/rollback path. The relief-assignment ledger remains outside this timetable preparation.

The source check is an administrator-supplied read-only observation, not a signed Google attestation. It proves the source agreed when exported; later changes can make it stale. Re-export and compare before handover. Imported snapshot status is never evidence of continuous production freshness.

Venue consumers in a later release should receive only the occupancy projection they are permitted to see, including the occupying teacher's necessary name. SMC drafts and unrelated private staff data must stay excluded.

9. Roll back only the rehearsal interface

In Workers & Pages → gsis-roster-rehearsal → Deployments, restore the tested I version recorded in section 2, or paste the saved tested I module and deploy it. Keep the existing bindings, markers, synthetic tables and bucket. O's preparation data can remain privately stored; it does not affect I's synthetic ledger or production. Do not delete either storage resource as a rollback step.
