# Edge queues with Google authority

Model: Codex. Design dated 8 November 2026, Asia/Singapore. Reviewer: Muse at the PR's exact head. This note proposes the contract for Deploy, then Venues, then Contacts. It implements nothing and authorizes no deployment or mode change.

The [task record](../tasks/edge-queue-google-authority.md) owns scope and verification. Google remains the system of record for app data, decisions, revisions, and duplicate protection. D1 owns pending command delivery and its receipt history, and holds replaceable read projections. A D1 acceptance is **Queued**, never **Saved**, **Published**, or a confirmed booking.

## Decisions and dependencies

- Use a shared command protocol and Worker service, with an app-specific adapter for Google authorization, revision checks, mutations, receipts, and read projection. Isolate each app in its own D1 database/binding and deployment configuration. The schema includes `app` in every key as a second isolation boundary.
- Start with `direct` for every app. A shadow period compares reads and exercises synthetic commands; it never dispatches a second copy of a real direct write. Only the owner enables `queued` after the app's acceptance gates pass.
- Serialize the entire Google workbook per app initially. Deploy's index/publication, Venues' cross-room occupancy, and Contacts' shared catalogues make narrower document locks unsafe without further evidence.
- New transport handlers use GSIS_SECRET only, validate its configuration, and fail closed. Contacts #102 and Calendar #104 are merged. Roster/Deploy consolidation is the next separate dependency before P1. This note does not migrate any app or reuse transport credentials as browser session keys.
- P1 builds on merged [Deploy-to-Contacts publish reporting #90](../tasks/deploy-contacts-catalogue-sync.md). Preserve its frozen publication identity, separate Contacts result, Layout result, and fenced retry. Do not re-implement that fix.
- Venues route suspension and the #67 stale fix are separate work. This queue neither enables a suspended route nor changes Roster authority or source routing. The live Contacts 401 outage remains owner-side configuration alignment.

## Existing LORD behavior and the admission-handler decision

Read [LORD phase 1](../tasks/lord-queued-writes.md), [its Worker](../../../lord-job-worker/worker.mjs), and [its schema](../../../lord-job-worker/schema.sql) as prior art, not as this design's completed implementation.

| Existing piece | Reuse and required difference |
| --- | --- |
| `authenticate` verifies a purpose-bound HMAC, a 60-second window, school actor, and nonce journal. | Reuse the envelope/nonce pattern with edge-specific purposes, app, document, and configuration generation. Use a fresh nonce for every transport retry while retaining the command ID. |
| `enqueue` binds an issued timestamp plus UUID, canonical actor/action/payload hash, SQL conditional admission, and exact retry. | Reuse canonical hashing and atomic cap checks. Preserve existing app UUID request IDs; store issuance time separately. Add app/document/revision binding and a server-allocated FIFO sequence. |
| `drain` claims a job using conditional `UPDATE ... RETURNING`, token, and a 120-second lease. | Reuse compare-and-swap and token-fenced checkpoints. Add a document head/gate: LORD's per-job claim and actor/action uniqueness do not enforce FIFO or one in-flight job across a whole workbook. |
| Expired `RUNNING` work becomes `CHECKING`; bounded unsuccessful checks become blocking `UNCERTAIN`. | Reuse read-only recovery. Never turn an expired lease or missing receipt into permission to execute again. |
| Exact version/digest backup acknowledgement gates terminal deletion after 30 days; unresolved work never expires. | Reuse verified export/retention. Keep Google app decisions and duplicate tombstones independently of D1 payload retirement. Do not import LORD's D1-authoritative queue backup as app-data authority. |

The earlier observation that `queueCommand` existed only in a test was a case-sensitive search error. At base `0c897a4`, [LORD backend `doPost`](../../../lord-suite/Source/backend/Code.gs) lowercases the action and dispatches `queuecommand` to `lordQueueCommand_` at lines 531 and 7485. That handler supports execute/status/backup, not D1 admission. It checks existing Google decision evidence before applying preferences, and status can return `UNKNOWN`. LORD phase 1 supports only `notificationPreferences`; it is not an implemented queue for all LORD actions.

**Decision:** edge admission lives in the Worker service's proposed `POST /commands`, input `kind: enqueue`. The authenticated app gateway signs the verified actor and validated command. Google has separate proposed execute, status, and cancellation adapters. Admission makes no Google mutation or Google queue insertion. Existing Google handlers cannot be advertised as edge adapters until the relevant phase implements and tests them. Handler names and tables below are proposed contracts.

## D1 records, limits, and retention

Use the same logical schema in each app's isolated database. IDs and scope keys come from server configuration, not a browser-supplied workbook URL. Times are UTC epoch milliseconds; UI times use Asia/Singapore.

| Record | Required fields and constraints |
| --- | --- |
| `edge_jobs` | `sequence INTEGER PRIMARY KEY` allocated on admission; `app`, `document_key`, `request_id`, `issued_at`, `actor_key`, minimal `actor_json`, `action`, `schema_version`, `expected_revision_json`, canonical `payload_json`, SHA-256 `payload_hash`, `state`, `result_kind`, `receipt_json`, fixed `error_code`, `created_at`, `updated_at`, `next_at`, `lease_token`, `lease_until`, `checks`, `dispatch_failures`, `version`, `exported_version`. Unique `(app, request_id)`. An existing ID with another actor, document, action, revision, or digest is a 409 mismatch. |
| `edge_receipt_index` | Compact terminal identity/result binding after a job payload is archived: `(app, request_id)` primary key, document, actor, action/schema, expected revision digest, payload hash, Google decision reference/digest, outcome/revision, export version/digest and timestamps. Never stores another copy of the business payload. |
| `edge_scopes` | Unique `(app, document_key)`; `mode`, `admission_paused`, `dispatch_paused`, `config_generation`, `head_sequence`, `active_request_id`, `lease_token`, `lease_until`. Unresolved head identity stays pinned when a lease expires. Mode changes require a verified Google configuration generation. |
| `edge_job_steps` | `(app, parent_request_id, step_key)` primary key; stable `child_request_id`, target app, publication/commit identity, state, attempt/check counts, target receipt and revision, safe error code, timestamps, version. A child result cannot overwrite the parent's Google-save outcome. |
| `edge_job_events` | `(app, request_id, event_sequence)` primary key; state transition, timestamp, token/version reference, safe outcome code and evidence digest. Latest 12 events may be embedded in a job response; older events remain in retained exports, not silently discarded. |
| `edge_nonces` | `(app, purpose, nonce)` unique, creation time and expiry. Three-minute retention exceeds the 60-second signature window. Atomic capacity limit 10,000 active rows per app. Full journal rejects admission; it never disables replay checking. |
| `edge_cache` | Key `(app, document_key, projection, audience_key, auth_revision, schema_version)` plus Google revision/commit, source digest, payload digest, verified source manifest, payload, fetched/verified timestamps and expiry. Queue high-water mark and known stale flag prevent treating a pre-write snapshot as current. |

Indexes: unique `(app, request_id)`; `(app, document_key, sequence)` for FIFO; `(app, state, next_at, lease_until)` for due work; `(app, actor_key, sequence)` for private receipt pagination; `(app, state, created_at)` for caps and health; nonce expiry; cache expiry and document/revision. A partial unique index on `(app, document_key)` for `RUNNING`/`CHECKING` supplements, but does not replace, the pinned-head rule for `UNCERTAIN`.

| App | Total retained job rows | Open jobs per app | Open jobs per actor | Canonical payload cap | Read-cache freshness limit |
| --- | --- | --- | --- | --- | --- |
| Deploy | 5,000 | 1,000 | 20 | 256 KiB | 5 minutes |
| Venues | 5,000 | 1,000 | 20 | 64 KiB | 60 seconds |
| Contacts | 5,000 | 1,000 | 10 | 256 KiB | 60 seconds |

Open means `QUEUED`, `RUNNING`, `CHECKING`, or `UNCERTAIN`; pending child steps count against the target app's limits when admitted there. Counts cover all actors and document scopes in that app's database. Service catalogue commands have a distinct service actor subject and the same bounded per-actor cap. Add no unbounded service bypass.

Payload limits count uncompressed canonical UTF-8 bytes, with at most 16 KiB additional envelope metadata. Stream reads stop at the limit. Reject larger commands with 413 before insertion; never split one atomic save silently. Large table saves need a separately designed bounded adapter before being queued. Cache entries are capped at 2 MiB and aggregate cache at 64 MiB per app, with ordinary cache eviction. Cache eviction never deletes jobs or receipts.

Retain unresolved jobs, payloads and evidence without age deletion. Refuse new admission at capacity rather than evict pending work. After 30 days, terminal job payloads/events may leave D1 only when the exact job version and digest have a verified private Google export. Private exports have a 365-day minimum retention; archive review must preserve unresolved evidence and the duplicate-protection ledger. A failed or ambiguous export keeps the row and applies backpressure. Move the compact receipt/tombstone into `edge_receipt_index` before deleting an exported terminal job row. Cap this index at 100,000 entries per app; at capacity, pause new admission for owner-reviewed archival rather than erase identities. Look up this index before new admission and serve its original exact-retry outcome. There is no automatic deletion of Google operation identities. This follows LORD payload retention without weakening the owner's keep-records rule.

### Google decision ledger

Every direct and queued mutation uses one app-local durable ledger, proposed `edge_operation_receipts`, under the existing app writer lock. Its key is `(app, document_key, request_id)`. It binds actor subject, action/schema, expected revision digest, payload hash, issued time, mode/configuration generation, and attempt fence. Fields include `decision` (`PREPARED`, `APPLIED`, `REJECTED`, `CANCELLED`), native journal/commit reference, before/after revision, outcome code, result digest, timestamps, and publication step identities.

The adapter writes durable intent before a mutation and associates its identity with the app's recoverable commit. A recovered commit and the corresponding decision must agree. The ledger is not an extra best-effort Sheet write after success: a crash between data and receipt must be recoverable through the native journal. Deploy's field commit, Venues' commit token, and Contacts' pending/catalogue journals need separate adapter proofs. An unrecoverable split stays uncertain and blocks that document.

A known exact replay returns the original decision without mutating again. Mismatched ID binding returns conflict. Unknown IDs first presented more than 24 hours after their authenticated issuance time cannot execute; existing decisions remain readable. A status read reporting no row is `UNKNOWN`, never proof of non-application. Tombstones remain queryable after bulky payload archival. Capacity or ledger corruption fails closed, not by trimming identity history.

## Admission and the one-second receipt

1. The browser creates one UUID request ID before sending, records the pending proposal locally, and reuses that ID on transport retry. The proposal includes its observed Google revision. A server-authenticated issuance time bounds new admission without changing existing app UUID formats.
2. The app gateway verifies the signed school session, same-origin/CSRF rules, identity type, allowed action, ownership/role and payload schema. It replaces all browser actor and scope fields. A service catalogue request uses its own restricted service identity instead of a browser cookie.
3. Worker role decisions use a Google-signed or server-verified role observation bound to actor, app, document, allowed action set, auth revision and expiry, maximum age 60 seconds. A stale/missing observation must be refreshed through authenticated Google reads before admission or return an explicit unadmitted response. No permissive cached default. Revocation can still occur during the window; Google rechecks before application. Queued never promises authority to apply.
4. The gateway sends `{purpose, app, document, configGeneration, timestamp, nonce, actor, command}` in a purpose-bound HMAC envelope using GSIS_SECRET. Purpose is `edge-command-gateway-v1`; backend execution uses a different purpose `edge-command-google-v1`. Status and step/service inputs have exact schemas. The service enforces the 60-second window and consumes a fresh nonce.
5. Compute `SHA256(canonical({app, document, actorSubject, action, schemaVersion, expectedRevision, payload}))`. Canonical JSON sorts object keys, preserves array order and rejects non-finite numbers, undefined values, duplicate JSON keys and schema-invalid fields. No implicit trimming or coercion of IDs/revisions. The digest is an identity binding, not a substitute for authorization.
6. Look up an existing `(app, request_id)` first. Exact retry returns that receipt even when new admission is paused or caps are full. A mismatch returns 409. Concurrent inserts use one atomic conditional insert/transaction that checks mode generation, pause flags, total/open/actor caps, and unique identity, allocates sequence, and commits the initial event. Catch a uniqueness race by rereading and comparing the entire binding; no separate count-then-insert race.
7. Return HTTP 202 with `{requestId, state: QUEUED, resultKind: pending, sequence, submittedAt, version, saved: false}` only after durable commit. Status/list are actor-private and paginated. D1 failure before an acknowledged receipt gives an unknown admission outcome until the same ID is checked, not a fabricated rejection.

The warm admission target is at most one second for a bounded command on a normal connection, measured from submit to durable receipt. Measure p95 and disclose network/cold authorization delay. Do not promise one second for a cold Google role check, an unavailable service, or an oversized proposal. Do not call Google mutations or wait for publish downstream steps in admission. Wake dispatch after commit and retain a scheduled poller so a lost wake does not lose work.

## Ordered dispatch and outcome recovery

The dispatcher selects the lowest open sequence in a scope, including future-backoff and uncertain rows. It cannot skip an unresolved head to find a ready later row. One atomic D1 transaction takes/renews the scope gate and conditional job claim with `UPDATE ... RETURNING`. A losing dispatcher receives no claim. This is required across concurrent cron, wake, and recovery invocations.

A claim has a random token, a 120-second lease and a monotonically increasing scope fence. Set a 35-second Google request deadline; lease time is coordination, not proof that Google stopped. Checkpoint only with the matching active request, token, fence and job version. If a response arrives after its token expired, it cannot overwrite a later reconciliation. Its Google decision remains available for a status check.

Google independently authenticates the service envelope, re-resolves identity/roles, and takes the existing writer lock. Inside the lock it recovers native pending commits, checks the operation ledger, verifies the scope/mode generation and expected revision, and applies only a previously unseen valid operation. Direct writes use that same lock and ledger. Revision checks happen at application time, not only admission. Preserve existing field conflict and lease rules; this phase does not invent automatic merges.

| Current state | Event and next state | Execution permission |
| --- | --- | --- |
| `QUEUED` | Exclusive head claim -> `RUNNING`. Definite pre-dispatch configuration/admission cancellation -> `REJECTED` with evidence. | Only the newly claimed head can send execute. |
| `RUNNING` | Exact Google decision -> `APPLIED` or `REJECTED`. Lost/invalid response, worker crash or expired lease -> `CHECKING`. | No second execute after any possible send. |
| `CHECKING` | Read-only Google decision/status -> `APPLIED`, `REJECTED`, or more checks. Five unsuccessful checks -> `UNCERTAIN`. | Status/reconciliation reads only. Use 15, 30, 60, 120 and 300-second bounded delays; keep the head pinned. |
| `UNCERTAIN` | Actor/Admin explicit **Check status** -> `CHECKING`; exact reconciled Google decision -> terminal. | Never execute/retry automatically. Lease expiry does not unblock the next job. |
| `APPLIED` | Google returned/recovered the exact operation, payload digest, and committed revision. | Terminal primary mutation; dependent steps and cache refresh have their own statuses. |
| `REJECTED` | Durable definite validation/permission rejection, cancellation fence, or revision conflict. | Terminal, no mutation retry under a new ID without user review. |

`Conflict` is `REJECTED` plus `result_kind: conflict`, not a seventh transport state. Record the submitted base and proposed change; fetch the current authorized Google version for comparison. Show both, retain the draft, and require a fresh user decision and new request ID. Do not auto-update the expected revision and requeue the old command.

A transport 4xx alone is insufficient evidence of non-application. The adapter must attest a rejection before any mutation, or return an exact ledger decision. Malformed success, auth proxy errors, provider timeouts and partial commit responses remain uncertain when a send may have happened.

Read-only checks do not run recovery writers hidden inside a GET. If the native app needs recovery writes, an explicit authorized recovery command resolves that journal first; its evidence is then read to settle the original queue job. Failure to prove either outcome leaves the scope blocked. An Admin may obtain a durable cancellation tombstone under the Google lock for a not-yet-decided request. That prevents a delayed execute from applying; absence of a receipt alone cannot authorize cancellation or replacement.

## Receipts, publish steps, and user experience

Every save retains its request ID and shows **Queued at HH:MM**, **Applying**, **Checking outcome**, **Needs review**, **Saved at HH:MM**, or **Rejected**. The pending-changes badge counts all nonterminal own jobs and unresolved own downstream steps. The user can keep a separate draft but cannot submit a dependent edit as though a queued version were already applied. An intentional sequence of edits requires a verified applied revision for each subsequent save. Reload/sign-in restores pending receipts without resending mutations.

Receipt JSON includes app/request/action, state/result kind, submitted and last-checked times, actor-visible before/after revision, safe outcome code, exact Google receipt reference/digest, schema/version, allowed recovery actions and dependent step summaries. It excludes raw secrets, endpoint URLs, private links, unauthorized values and provider errors. Only current authorization can fetch the comparison version. Another actor cannot enumerate receipts by guessing IDs; an Admin has a separately audited view.

For Deploy publish, keep distinct steps: **Deploy publication**, **Contacts catalogue**, **Layout handoff**, and any existing **Roster reference/snapshot handoff** supported by that publication path. Record `not_required` with a reason for absent/configured-off steps; never invent or enable a Roster writer to fill a status row. An applied Deploy publication with a failed Contacts step says **Published; Contacts update pending/failed**, not total success or total failure. Parent `APPLIED` never rolls back or re-publishes to repair a child.

In P1 reuse #90's synchronous Contacts/ Layout reports and explicit retry entry points. Each supported retry is an independently receipted command with a stable child ID bound to the frozen publication commit/catalogue revision and step. `retryContactsSync_` requires a fresh request ID distinct from the original publish ID; preserve that rule. A lost child response checks its same ID/revision/digest before retry. A superseded publication rejects an obsolete retry; it must not write newer or older catalogues under the wrong identity. Missing step-status adapters block queued enablement for that step rather than claiming exactly-once behavior.

In P3, the Contacts catalogue step becomes a Contacts queued command. Deploy records its returned child receipt, not a claim that Contacts applied it. Authenticate the originating actor and restricted Deploy publication service, verify current privilege at Contacts, and bind `applyDeployCatalogues` to the frozen payload and expected Contacts base. A newer catalogue revision or same-revision/different-digest is a conflict. Do not replay the parent publish. Cross-app children are admitted outside the parent's Google writer lock, after durable publication, to avoid holding one app lock while waiting for another. Reconciliation resumes from the stored step identity.

## Verified cache and direct reads

Each cache response names the Google revision, commit/digest and verification time. Display **As of HH:MM SGT, revision N**; for digest-based Contacts revisions, N is the real short revision token, not an invented numeric counter. Pending proposals remain separate from saved rows. D1 mutation acceptance cannot update a verified cache as if Google had saved it.

A signed Google projection manifest binds app, document, schema, audience/authorization revision, data revision, payload digest, generation, and observation time. Verify the signature and recompute the digest before storing. Do not use a digest computed only over a D1 copy as evidence of Google origin. Read the Google revision before and after projection construction; publish only a consistent observation with no native pending commit. Normal writes or sheet edits outside managed app paths can invalidate revision tokens; until an adapter detects them reliably through a Google content digest, its affected projection stays direct.

After every applied write, mark all affected cache entries stale before serving the result and schedule a verified refresh. A refresh error does not undo an applied receipt. An in-flight older refresh cannot overwrite a newer verified generation/revision. Read from the D1 primary/consistent session so known-write invalidations and own-write high-water marks are observed. Pin a read after save to at least the applied Google revision, or read Google.

Refresh Deploy every five minutes while used and Venues/Contacts every minute while used, plus after application and on demand. Coalesce refreshes per scope to avoid lock pressure. Enforce the per-app maximum ages above at read time even if the scheduled task did not run. Cache-only role/permission inference is forbidden; privileged/private projections require the current bounded-age authorization observation. System Health, receipt checks, recovery and permission-sensitive decisions remain direct or use their explicit authenticated services.

Missing, expired, unverifiable, audience-mismatched, pending-commit or known-stale cache means direct authenticated Google read, then verified refresh. If Google is unavailable too, show the last verified view only as explicitly stale/read-only with its original time, or show unavailable. Never report an empty directory, free venue or zero entitlement as a fallback. Cache freshness never overrides expected-revision checks at Google.

## Direct fallback with the same operation identity

Mode `direct | queued` is an Admin setting per app, default `direct`, stored as Google-authoritative configuration with a monotonic generation and mirrored into D1. New admission fails closed on unknown or mismatched generation. Changing configuration requires Admin authorization and a verified acknowledgement; this docs PR changes no setting.

A queue admission response can be lost after insertion. The client keeps the original ID/payload digest, queries its receipt where reachable, and never generates a replacement ID on timeout. If Worker/D1 is unavailable, fallback submits that same operation to the authenticated direct Google adapter. Both paths consult the same Google ledger under the same writer lock. If either already applied, the other returns the exact duplicate receipt. If the operation is prepared/pending, the other checks and reports uncertainty rather than executing another copy. Reconciliation later brings D1's state into agreement.

This is a deliberate difference from LORD's phase-1 rule forbidding direct replay of an admitted operation: edge fallback is safe only after both direct and queued adapters share durable deduplication, mode checks, and native-journal recovery. P1 cannot claim fallback based solely on today's bounded Deploy request list, Venues' time-pruned receipts, or a D1 query returning not found.

**Independent route decision:** a different path on the same failed Pages Worker is not a fallback for Worker unavailability. Each app needs a separately reachable Google-hosted recovery page/endpoint that validates a Google school identity token server-side against the configured audience, issuer, expiry, verified email/subject, and login nonce. Apply origin/CSRF protections, current roles and the same ledger contract; never send GSIS_SECRET or a private backend key to the browser. A D1-only outage can use the surviving authenticated app gateway to reach the same direct adapter. The full Worker-outage path uses the Google-hosted page, preserving the staged proposal/ID by explicit user continuation. It does not interpret a lost response as permission to invent another ID.

This recovery page and its tested browser/token-delivery flow are future implementation requirements, not existing features. If an app lacks that independently reachable authenticated path, or cannot safely pass its proposal and ID, it must retain the pending receipt/draft and explain that direct continuation is unavailable. That app cannot enable `queued` until the required fallback exists. A second Worker may help a single-deployment failure but cannot prove recovery from a Cloudflare-wide outage. Credential-bearing payloads and staff details must not travel in URL query strings.

A direct fallback during an outage can overtake D1-only jobs. FIFO is guaranteed within queued delivery, not across an unavailable queue and direct Google traffic. Google revision checks decide the direct outcome; later queued stale proposals become conflicts for user review. Never bypass an unresolved Google intent/commit to get availability. No fallback route clears locks, assumes a lease expired at Google, or blindly repeats downstream publication steps.

## Switch-back and recovery

1. Pause new queue admission for the app. Continue exact receipt/status reads. Establish an Admin-owned cutover generation in Google and mirror it to the dispatcher.
2. Drain known pending work in FIFO order while retaining the gate, or pause dispatch and export every pending job, binding, event, lease/fence, dependent step, and cache/Google revision reference. The export is private, versioned and digest-verified. An export alone does not settle a write.
3. Wait for active calls and reconcile `RUNNING`, `CHECKING` and `UNCERTAIN` against Google. Verify every applied operation's recorded revision/commit through its ledger and native evidence, including step outcomes. Current head revision alone cannot prove a historical receipt. Missing retained evidence blocks an all-clear report.
4. For jobs left unexecuted, write/verify Google cancellation fences for the original IDs under the existing writer lock. Late dispatches then return a known cancellation. Unresolved prepared commits remain blocked; export them and retain the scope hold. Never mark them rejected just to complete cutover.
5. Produce an app reconciliation manifest with counts, IDs/digests, exact applied/rejected/cancelled/uncertain evidence, pending step ownership and any held document. Pause remaining queue dispatch and advance Google configuration generation to direct only when no old execute can bypass those fences. Mode direct is not permission to write a still-held scope.
6. Set and verify Admin mode `direct`, reconcile the D1 mirror, retain the paused database/export and original receipts, and test direct duplicate lookup before resuming normal work. Do not replay exported pending payloads as new commands. A failed cutover retains the pause/holds and last verified configuration; no automatic route oscillation.

Restoring a D1 database uses the same manifest and Google reconciliation. A newer Google decision supersedes an older D1 state; neither a cache nor a blank database may overwrite app records. Loss of D1 cannot be resolved by declaring unresolved commands unsubmitted.

## Health, security, and privacy

Per-app System Health exposes queue mode/configuration generation, admission/dispatch pause, total/open depth by state, oldest pending age, active scope hold, last applied time/revision, dispatch failure count, cache age/verification failure, export backlog and last successful reconciliation. User screens show only their own receipts and safe service availability. Do not expose actor lists, payloads or raw provider logs in a public health endpoint.

Alert Admins when oldest pending exceeds 10 minutes or two consecutive dispatch attempts for an app fail. Count failed transport/application attempts, not ordinary revision conflicts; show permanent rejections separately. Deduplicate the alert per app/incident, include queue age, count and a protected recovery-screen link, and resolve it when the blocker clears. Do not page staff or send payloads/private links. Actual alert delivery is an app phase implementation and test, not an authorized send here.

Every network hop authenticates actor and app/purpose; Google repeats current role and ownership checks under its mutation boundary. The shared transport secret is not proof of a human role, is never a cookie signer, and cannot choose an unrestricted service action or arbitrary URL. Worker configuration maps app to trusted backend and database. Browser-supplied app/document/actor fields cannot select another app's rows. Receipt reads/checks, cache audience selection and admin alert/recovery actions enforce the same isolation.

Store only the actor identifiers and business fields required to execute the command. No tokens, secrets, passwords, private relief links, session cookies or raw provider responses in payloads, events or logs. Necessary staff edit content is access-controlled operational data, not telemetry; redact it from errors and apply the stated payload/export retention. Logs contain app, opaque request ID, transition/version, latency and fixed outcome code. Protect private Google exports and use no public-share links. Invalid signatures/configuration and stale grants fail closed before admission; a lost dispatch result remains uncertain, not rejected for convenience.
