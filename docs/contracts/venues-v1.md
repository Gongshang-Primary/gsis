# Venues v1 contract

Implementation baseline: f1069a1. The user approved building the reviewed Venues product and permits its own Apps Script. Follow the product design, with the standalone coordination choice below. All dates use Asia/Singapore, ISO YYYY-MM-DD; intervals are half open integer minutes [start,end). Stable IDs never derive from mutable names. Date-effective publication scope replaces the original single-year setting.

## Ownership

Venues Apps Script owns bookings, separate facilities permissions, policies, closures, audit, receipts, source fence and outbox in its own spreadsheet. Roster owns effective timetable occupancy. Contacts owns staff identity/contact data. Deploy owns the immutable published physical room register used for each booking date; Layout retains its separate campus publication. Calendar owns covered dates and parity. Browser caches are hints and never authorise writes.

Roster sends signed begin to Venues before its canonical mutable source commit and complete after the commit. Begin is durable and blocks admission. Complete marks source stale; it does not activate old content. Each begin has a unique token and compare-and-set source revision; stale completions cannot clear newer pending work. A missing or ambiguous acknowledgement blocks the source commit or leaves the fence pending. Explicit recovery verifies Roster source under its writer lock before completing that token. Never clear pending on age alone. Venues sync never holds its own lock during remote reads. It fetches all sources, builds a pinned projection, then activates only if the fence/token and captured source revisions still match. Timetable displacement, audit and outbox intent are committed together. No claim of atomicity across Google services.

Coordination is enabled when Roster has VENUES_APPS_SCRIPT_URL and VENUES_BRIDGE_SECRET. Partial configuration fails closed. With neither configured, all existing Roster behaviour continues without new network calls. Final setup enables this only after Venues is deployed and verified.

## Browser transport

POST /api/read and POST /api/command. Same origin only. Normal authentication is a verified Google school JWT (`GOOGLE_CLIENT_ID`) or its seven-day host-only Secure, HttpOnly, SameSite=Lax session cookie. An optional configured Cloudflare Access assertion is verified by signature, issuer, audience and time claims. Server reads current active Contacts identity and facilities grants for every private operation. Public assets and short-route sign-in shells do not expose private data. Browser cannot supply a role, staff identity or authoritative source. Every command includes requestId (UUID) and expectedRevision (nonnegative integer). A new booking treats the global revision as an observation, not a ban on independent bookings; current interval/policy checks still apply. Per-record conflicts are authoritative. No business mutation occurs on GET. `/b/<id>` and `/r/<id>` load the sign-in shell with the selected record; opening a link grants no authority. Public auth/config routes are GET `/api/config`, GET or POST `/api/session`, and POST `/api/logout`. POST session requires a verified Google bearer JWT. API body streaming is bounded to 65,536 bytes; both read and command POST routes require exact same origin and reject cross-site Fetch Metadata.

Response envelope: {ok:true,data:...} or {ok:false,status,code,error,conflicts?}. Backend signed envelope: {payload:JSON.stringify({action:'venues',timestamp,nonce,identity:{email,subject},input}),signature:<HMAC SHA256 hex>}. Signature key VENUES_PROXY_SECRET. Input has operation plus fields below. Read/command classification enforced in Worker and backend. Service envelope uses action:'venuesService', service:'gsis-venues-v1', timestamp,nonce,input and VENUES_BRIDGE_SECRET. Source bridges use action:'venuesSource', service:'gsis-venues-v1', source:'roster'|'contacts'|'deploy'|'calendar',timestamp,nonce,input with same bridge key. No school-user identity accepted by service endpoints.

## Data shapes

Actor {id,name,email}; permissions {admin:boolean,ownedVenueIds:string[]}. Staff list is {id,name,active} only, and only authorised management users receive it. Venue {id,unit,name,descriptors:string[],aliases:string[],bookable:boolean,special:boolean,approvalMode:'immediate'|'approval',open:'07:00',close:'18:00',capacity:number,features:string[],bufferMinutes:number,overlapGroup:string,ownerIds:string[],revision:number}. Aliases preserve old timetable room names; ids are assigned UUIDs. Policy changes do not rewrite booking status.

Period {id,label,start,end}, minute integers. Occurrence {id,seriesId,venueId,date,periodIds:string[],intervals:[{start,end}],requesterId,ownerId,requesterName,ownerName,note,status:'pending'|'confirmed'|'cancelled'|'rejected'|'displaced',revision,sourceGeneration,createdAt,updatedAt,ownerResponses:[{actorId,actorName,at,text}]}. A series has one venue and date range/weekday recurrence; each date occurrence retains own owner and note. Only adjacent selected periods are grouped. Unknown/uncovered date cannot be booked.

Transfer {id,kind:'booking'|'timetable',bookingId?,venueId,date,periodIds,sourceGeneration,requesterId,requesterName,originalOwnerId?,note,status:'pending'|'accepted'|'rejected'|'cancelled',revision}. Accepting an ad hoc transfer changes that occurrence owner only. Timetable acceptance creates waiver and beneficiary occurrence together; waiver is scoped to the verified dated timetable and exact interval. Holds are not released by transfer requests. Latest source revalidates waivers. Adding unrelated future-year coverage carries a waiver and pending timetable transfer forward only when that date’s verified publication, periods and occupancy remain unchanged. Changed dated authority still invalidates the waiver.

Grant {id,kind:'admin'|'owner',staffId,venueId?,active,from,to,revision}. Only admins can manage grants; last active admin is protected. Owners manage only granted rooms. Self-approval requires explicit separate decision and audit attribution. Support staff can be owners.

## Reads

bootstrap -> {version,actor,permissions,venues,periods,manifest,revision,policyRevision,staff?,source:{status,checkedAt,error?}}.
manifest -> {manifest,source}, with the same trusted source status. piece {key} -> {key,encoding:'gzip-base64-v1',data,sha256,bytes}. bookings {from,to,venueIds?:[],mine?:boolean} -> {revision,occurrences,transfers,closures,permissions,policyRevision,source}; bound date ranges to 366 inclusive. Short links use bookings {id} or bookings {transferId}, exactly one selector, without a date range. The backend checks current requester/owner/room-management authority, returns the selected record plus authorised related booking/transfer records, and includes closures covering its room/date. admin -> {permissions,coverage,utilisation,closures,grants,venues,approvals,transfers,displaced,deliveryFailures,audit,source,revision}. The admin closures list includes all closures within the caller's room-management scope, not only those overlapping a dashboard date range. Manager-only source diagnostics add unresolvedAliases:string[] and mappingIssues:object[]; unknown or ambiguous aliases mark affected dates uncovered even if the manifest itself is ready. Alias edits are admin-only and force source re-projection. Only scoped data/PII is returned, no recipient contacts or secrets.

## Commands

book {venueId,dates:string[],periodIds:string[],note,availableOnly?:boolean}. Validate all dates before commit. Default whole selected request rejects on any conflict; explicit availableOnly skips conflicting dates with response skipped. Immediate ordinary series: first date confirmed and later pending; special series: all pending. Approval rooms: all pending. Pending holds have no automatic expiry. Policy is server-fresh.
amend {id,revision,note?,date?,periodIds?}, or bulk-note-only amend {ids:[{id,revision}],note}; bulk amendment cannot also change date/periods or supply a single id. cancel {ids:[{id,revision}],reason?}; decide {ids:[{id,revision}],decision:'approve'|'reject',reason?}; requestTransfer {kind,bookingId?,bookingRevision?,venueId,date,periodIds,note}; decideTransfer {id,revision,decision:'accept'|'reject',reason?}; respond {id,revision,text}; saveVenue {venue:<fields>,revision}; saveGrant {grant:<fields>,revision?}; saveClosure {closure:{id?,venueId,from,to,start,end,note,active},revision?}; sync {}; notificationDecision {id,revision,decision:'confirmSent'|'retry',reason}. Every successful mutation returns {revision,occurrences:changedRows,transfers:changedRows,venues?:changedRows,closures?:changedRows,permissions?,message,skipped?:[],delivery:{queued,failed,uncertain}}. saveClosure returns its changed closure in result.closures so the client can update its current rows without reloading the source package. Return fresh scoped permission changes, preserve requester text and append owner responses. Admin summary supports pending, displaced, failed/uncertain/setup-required delivery and utilisation. Bulk decisions and cancellations list explicit record IDs/revisions; historical series ownership never grants cancellation of an occurrence transferred to someone else. Notification review requires a reason, preserves already-sent channels and is blocked while a channel is sending.

## Immutable occupancy cache

Manifest {schema:1,generation,updatedAt,checkedAt,from,to,pieces:[{key,sha256,bytes,encoding:'gzip-base64-v1'}],status:'ready'|'pending'|'stale'|'unavailable'}. SHA256 is lowercase hex over compressed bytes; bytes is uncompressed UTF8 length. Piece JSON {schema:1,periods,days:[{date,covered:boolean,patternId,venueIds?:string[],periodIds?:string[],publicationKey?:string}],patterns:{[id]:[{venueId,start,end,sourceId,kind:'timetable',label:'Timetable'|'Confirmed timetable'}]}}. All fields whitelisted; no teacher names, free-text plan titles or contact data. The current coordinator stores one immutable piece per covered calendar year. Dated venue IDs and period IDs restrict both the booking grid and server admission; missing lists remain compatible with prior cached packages. Different year timings receive distinct period IDs. Cache scoped to actor; atomically switch generation only after every digest and byte-length check. Matching server generation/updatedAt reuses payload. Independent booking revision updates never invalidate occupancy pieces. Date/filter/Now navigation stays local.

## Source backend calls

roster input {operation:'manifest'|'snapshot',from,to,calendarDates:[{date,schoolDay,parity}],knownKey?,expectedKey?}; response {schema:1,source:'roster',key,observedAt,updatedAt,authoritative:true,unchanged?,periods,days,patterns}. Raw occupied intervals use venueAlias (not venueId), never teacher/class metadata. Missing aliases are reported and block affected dates until mapped. Entire selected year needs explicit Calendar coverage. Baseline every teacher block contributes; confirmed immutable suspended plans supersede baseline and published final relief deltas apply. Draft suspended edits do not contribute.
contacts input {operation:'manifest'|'snapshot',knownKey?,expectedKey?} -> {schema,source,key,observedAt,authoritative,unchanged?,people:[{id,name,active,email,cesEmail,mobile}]}.
deploy manifest input {operation:'manifest',knownKey?} -> {schema,source,key,observedAt,authoritative,unchanged?,publications:[{versionId,revision,commit,updatedAt,from,to}]}. The key covers the exact immutable publication references. Snapshot input {operation:'snapshot',versionId,commit,expectedKey} -> {schema,source,key,observedAt,authoritative,publication,venues:[{sourceId,unit,name,shortName,aliases,capacity}]}. The snapshot reads only the selected frozen published room register. Editable versions and the latest Layout head are not booking authority. Each date requires exactly one published effective window plus verified Calendar/Roster coverage. Overlaps, gaps, missing dates and unresolved aliases remain unavailable. Unchanged publication references and annual timetable pieces are reused independently.
calendar manifest input {operation:'manifest',year,knownKey?,expectedKey?} -> {schema:1,source:'calendar',key,observedAt,authoritative:true,unchanged?}. Dates input {operation:'dates',dates:<=62 unique ISO dates from one year} -> {schema,source,key,observedAt,authoritative,dates:[{date,schoolDay?,parity?,code?}]}. All batches must share the checked manifest key. Unchanged manifest reuses saved annual dates. Explicit holidays/weekends with schoolDay:false are covered; unknown dates carry a code and stay unbookable.
Source transport validates envelope, expected source, authoritative fields, expected key and a trusted observation within 60 seconds. Failure never returns invented empty availability. Fresh activation rechecks all source keys after slow snapshot preparation and verifies the captured local source/policy revisions under the writer lock. Unchanged source manifests reuse occupancy bytes; Contacts identity checks remain current.

## Settings and jobs

Venues Script Properties: VENUES_SPREADSHEET_ID, VENUES_SNAPSHOT_FOLDER_ID, VENUES_PROXY_SECRET, VENUES_BRIDGE_SECRET, VENUES_ROSTER_APPS_SCRIPT_URL, VENUES_CONTACTS_APPS_SCRIPT_URL, VENUES_DEPLOY_APPS_SCRIPT_URL, VENUES_CALENDAR_APPS_SCRIPT_URL, VENUES_ADMIN_EMAILS (initial bootstrap only), VENUES_PUBLIC_URL, optional WhatsApp provider settings documented by implementation. Pages: required VENUES_BACKEND_URL and VENUES_PROXY_SECRET, plus GOOGLE_CLIENT_ID for normal sign-in. Optional Access path requires ACCESS_TEAM_DOMAIN and ACCESS_AUD together; an Access-only deployment can omit GOOGLE_CLIENT_ID. Team domain accepts the name.cloudflareaccess.com hostname with optional HTTPS prefix/trailing slash; audience is the Access application AUD string. No live secret values in source or docs. Durable receipts/queues in tables, bounded retention pruning, never per-request Script Properties. Backend uses Sheets advanced API atomic batchUpdate and Drive API v3 snapshots. The upstream Contacts Venues source endpoint and matching VENUES_BRIDGE_SECRET must be published before setupVenues(), because initial admin bootstrap calls Contacts. VENUES_ADMIN_EMAILS accepts comma/semicolon/newline-separated emails and is used only when no admin grant exists. setupVenues() creates missing tables/resources and the minute trigger idempotently; retain generated IDs and rerun after an interrupted setup instead of clearing state. Jobs sync sources, reconcile displacements and dispatch notifications in bounded batches, with ambiguity states and backoff.

`VENUES_SCHOOL_YEAR` is ignored; leave any existing value untouched. Scope comes from the retained published Deploy effective windows, with no annual property rollover and no new secret, Script Property, binding or trigger requirement. An installation with no valid immutable published reference has no bookable date. At the first new publication, Deploy retains its known current immutable published pointer along with the new one, and then retains the latest publication of each version. Earlier pointers already discarded by older releases cannot be reconstructed from drafts. Review and explicitly publish missing versions with valid, non-overlapping effective dates before using those dates. Retention is bounded to 200 distinct published versions, retaining the newest snapshot of each. Publication preflight rejects exceeding this bound before storage writes; the existing index byte-size limit also remains enforced. No retained reference is silently dropped. See `docs/VENUES_SETUP.md`.

Notifications: successful bookings and accepted transfers to relevant participants, both CES/GSPS email addresses and WhatsApp. Use approved venue-compatible template configuration only; absent configuration yields visible setup-required queue state, never a false sent status. Management links authenticated, own-domain /b/id and /r/id. No live sends during tests or packaging. Preserve provider uncertainty; no automatic duplicate resend after ambiguous acceptance.


## Implemented setup and recovery entrypoints

The backend exposes operator functions `setupVenues()`, `venuesHealthCheck()`, `syncVenuesSources()`, `venuesRunJobs()`, `venuesPruneReceipts()` and `venuesRecoverCommit(expectedToken,evidence)`. The last function is not an HTTP command: it requires a matching current pending token and explicit evidence before resolving an unproven Sheets outcome. `VENUES_COMMIT_PENDING` is one fixed managed recovery marker, never a per-request accumulation.

After deploying Venues, configure both Roster coordination properties last, then run Roster `recoverRosterVenuesSource()` under its writer lock and Venues `syncVenuesSources()`. Roster `ROSTER_VENUES_SOURCE` is managed state. The signed source service accepts `{operation:'sourceStatus',source:'roster'}`, `{operation:'sourceBegin',source:'roster',token,expectedRevision}` and `{operation:'sourceComplete',source:'roster',token,revision}`. Results contain revision, pendingToken and status. Begin is repeatable only for the same token/expected revision; completion cannot clear another pending token. Neither marker expires into readiness.

Exact tables: VenuesMeta, VenuePolicy, AdminGrant, RoomOwnerGrant, BookingSeries, BookingOccurrence, TransferRequest, ApprovalDecision, Closure, TimetableWaiver, NotificationOutbox, AuditEvent, RequestReceipt, TransportNonce and StaffSnapshot. Literal JSON is chunked into cells of at most 40,000 characters; submitted transaction payloads are capped at 8 MB UTF8. Reads use complete authoritative tables under the school writer lock; writes patch only changed spans and include audit/receipt/outbox intent. Metadata keys are stored separately so a reservation counter update does not rewrite occupancy. This is a bounded school-scale design, not row-isolated SQL storage.

Delivery Script Properties: VENUES_EMAIL_ENABLED, VENUES_WHATSAPP_ENABLED, VENUES_WHATSAPP_ACCESS_TOKEN, VENUES_WHATSAPP_BUSINESS_ACCOUNT_ID, VENUES_WHATSAPP_PHONE_NUMBER_ID, VENUES_WHATSAPP_API_VERSION and VENUES_WHATSAPP_TEMPLATE, plus VENUES_PUBLIC_URL. Flags enable only on exact true. Operational notices use the school-managed agreement; no per-staff opt-in list. Template JSON is `{name,language,body,fields:[recipient_name,event,venue,date,status,manage_url]}` with string field names, exact provider-approved body/locale and six sequential placeholders. Body must mention venues. Dynamic headers and buttons are unsupported; static text headers/footers are allowed. Missing/unapproved configuration is setup-required.

Jobs attempt at most ten channels in a 45-second delivery budget. Sending claims that do not settle become uncertain after ten minutes, never auto-resend. Definitive rejection backs off; uncertain acceptance needs reviewed notificationDecision. Bounded background pruning removes up to 100 expired rows per table each run: receipts after 30 days, nonces after two days, sent outbox after 90 days. Failed/uncertain work remains. Snapshot pruning considers at most 20 files and removes only inactive managed occupancy snapshots older than 30 days.
