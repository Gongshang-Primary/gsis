# Rust-inspired engineering for JavaScript, Workers and D1

These are design and verification obligations, not Rust syntax, a language migration, or a claim that JavaScript has borrow checking. Use ordinary modules, explicit contracts and runtime checks. Add machinery only when the approved task needs it. [V1 instructions](../AGENTS.md) control scope and priority; [quality gates](QUALITY_GATES.md) specify how evidence is reviewed.

| ID and principle | JavaScript / Cloudflare application | Observable acceptance evidence |
| --- | --- | --- |
| R01 Single ownership | Name one responsible domain for each authoritative field, state transition and write operation. Route commands to that owner through an authenticated interface; consumers cannot write another domain's authority. School ownership must be explicit in keys and queries. | A field/transition ownership map and call paths; negative tests reject wrong-domain, wrong-school and unauthorised writes. No competing writer bypasses the owner. |
| R02 Borrow rather than duplicate | Read versioned, minimal projections with owner, school, schema version and source revision. Consumers may retain permitted caches/read models with documented freshness and invalidation rules, but cannot promote them to authority. JavaScript references are not ownership enforcement: copy/validate external objects before retaining them. | Trace each derived field to its source. Test stale, missing, revoked and foreign-school projections and attempted mutation of a retained input. Explain permitted cache behaviour and failure semantics. |
| R03 Immutable publication | Publish a durable revision; do not retrospectively mutate its meaning. Corrections produce a new revision with provenance and an explicit relationship to the superseded record. Separate drafts from published records. | Tests show the earlier publication remains unchanged after correction, and consumers select the correct effective revision. Applicable retention/privacy rules still govern storage; immutability is not indefinite retention authorisation. |
| R04 Make invalid states difficult to represent | Use explicit tagged variants and validated schemas instead of overlapping flags such as success=true with pending=true. Handle every documented state/transition; reject unknown variants. JSDoc/types can assist but cannot validate untrusted JSON. | A state/transition table, legal and illegal transition tests, missing-field/unknown-version cases and exhaustive handler checks. A pending receipt cannot satisfy an applied-result branch. |
| R05 No unchecked assumptions | Validate client input, stored records, service responses and migrated data at trust boundaries: shape, version, size, identifiers, school, permissions and semantic invariants. Authenticate service identity independently of supplied fields. Use parameterised D1 queries and minimal projections. | Negative cases cover tampering, malformed/stale records, unavailable providers, school isolation and permission revocation. Secrets/PII never appear in error bodies or diagnostic fixtures. |
| R06 Explicit error handling | Contracts distinguish denial, conflict, unavailable, accepted/pending, confirmed applied and unknown outcome. Include stable reason codes and deliberate retry semantics; propagate uncertainty. Log only permitted metadata and do not swallow exceptions into success. | Tests inspect error classes and durable effects, not merely HTTP status. Simulate missing/malformed receipts, timeout and partial failure. An acknowledgement is never reported as saved/published/delivered without evidence. |
| R07 Controlled concurrency | Use expected revisions, owner-enforced fencing tokens, bounded leases and stable operation IDs where required by the operation. Lease expiry or an isolate-local map alone cannot stop a stale writer. Fence at the owning commit boundary. Scope ordering to the actual request/resource invariant, not an entire session without reason. | Controlled interleavings test competing writes, lease expiry, stale token/revision rejection, duplicate IDs and unrelated-resource concurrency. Document unresolved check-to-commit intervals rather than claiming a distributed lock. |
| R08 Transaction discipline | Group related writes atomically within the owning D1 database using supported transactional operations (for example a transactional D1 batch with constraints). Put preconditions and dependent writes in the same atomic boundary; an earlier SELECT followed by a batch is not an atomic guard. Never assume arbitrary interactive BEGIN/COMMIT across Worker calls. | Failure injection proves rollback of the whole owned write set and rejection of stale preconditions. Verify actual D1 API semantics. Separate D1 databases, queues and external providers need explicit operation states, reconciliation or compensation; no cross-D1 atomicity claim. |
| R09 Safe recovery | Preserve operation ID and intent across retries, persist deduplication/results within the owner as required, and reject reuse of an ID for different intent. After a timeout, reconcile durable state before retrying a possibly committed write. Bound retry attempts and define terminal/manual recovery states. | Test crash/timeout before and after commit, duplicate/out-of-order delivery and reconciliation of an unknown outcome. Verify one intended durable effect; do not claim exactly-once delivery from queue semantics. Compensation is a recorded new action, not erased history. |
| R10 Minimal mutable state | Prefer pure policy functions, immutable snapshots and narrow persistence adapters. Inject providers and clocks for deterministic checks. Avoid mutable global authority in Worker isolates; they are neither durable nor shared consistently. A shallow Object.freeze does not make nested data immutable. | Test input aliasing, repeated evaluation and isolation across requests/schools. Identify every mutable store and its lifetime; prove lifecycle limits and reset behaviour without relying on isolate reuse. |
| R11 Resource discipline | Specify bounds for payloads, rows, memory, CPU/work, parallelism, timeouts, retries/backoff and background work. Paginate or stream where needed. A Promise timeout may not cancel the underlying operation; prevent late completion from creating untracked writes. waitUntil is not a durable job ledger. | Test at/over each relevant bound, slow/late provider completion, retry exhaustion and backlog behaviour. Measure the changed hot path when performance matters. Record numeric budgets and Cloudflare limits applicable to the approved environment. |
| R12 Evidence before completion | Verify observable invariants and failure/recovery cases with synthetic identities and controlled clocks where possible. Use real boundary integrations only when authorised. Compilation, mocks and text matching alone cannot prove concurrency, persistence or security. | Link actual commands, exact tested SHA, outputs, negative controls and omissions. Distinguish unit/contract, integration, CI, browser/runtime UAT and deployment evidence. Never mark an unperformed gate passed. |

## Applying the principles without overbuilding

For a new operation, write a short contract that identifies its owner, input/output variants, trust boundary, invariants, publication rules, atomic boundary, concurrency scope, recovery path and resource bounds. Reuse an existing adequate contract rather than adding a framework. Explain which R01–R12 checks apply; a read-only pure function does not need a lease, queue or D1 transaction.

For a D1-backed mutation, approval to evaluate authority is not approval to commit later. Name who revalidates authority, when the storage precondition is enforced and what can change between them. If authority lives in another database, state the remaining race and the integration gate. Single-owner writes and idempotency do not eliminate that interval.

These standards do not reopen approved GSiS permission policy or promise guarantees absent from the current tranche. Document existing accepted limitations and carry them into later acceptance checks; stronger guarantees need an approved design and evidence.
