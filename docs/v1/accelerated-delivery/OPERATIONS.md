See [release inventory](RELEASE.md), [verification](VERIFICATION.md) and [interfaces](INTERFACES.md). Production v0.9 coordination remains with Muse; v1 coordination remains with ChatGPT. Claude independently reviews the exact implementation head before owner release decisions.

## Ownership transfer and operational checks

Keep exactly one scheduler/sender/webhook owner during coexistence. A future owner-approved cutover records the final old-system operation/receipt boundary, pauses old writers and senders, checks readiness and immutable source versions, then explicitly changes `SCHEDULER_OWNER`, `SEND_OWNER`, `WEBHOOK_OWNER` and the public webhook route for the selected integration. No automatic token change is involved. Do not activate both systems for the same reminder. The initial deployment workflow intentionally rejects enabling these values; cutover is a separately approved configuration procedure after staging evidence.

WhatsApp webhooks retain the provider's raw-body HMAC verification. Telegram webhooks retain their configured secret verification. Their dedicated handlers deduplicate provider events and cannot invoke an arbitrary user operation. External Roster links and LORD signage credentials are purpose scoped; neither establishes a general staff session. Keep link tokens out of logs and screenshots.

Admin System Health reads each owner's current build/schema, operation states, unresolved source pins, outbox age/state, integration ownership/configuration presence and recent verified backups. It reveals configuration presence, never secret values. Use the original operation ID to investigate a pending or uncertain save. The same ID and canonical intent return the original durable outcome; changed intent conflicts. Request IDs are attempt references. Never clear a source pin solely because its time elapsed: first prove the destination committed or fence it as aborted, then reconcile the original identity.

Provider dispatch is bounded through response-body consumption. Accepted, delivered, failed and uncertain have different meanings. Lease expiry or a lost/malformed successful response can mean a provider already accepted the operation; those jobs are retained uncertain. Retry only after provider/result reconciliation with the original stable identity. Google Calendar uses stable event IDs and etags; Drive creates use a persisted generated file ID. A failed external continuity export does not undo a committed school operation or erase its last successful artifact.

## Backup and isolated restore

Admin System Health creates per-owner backups through `/api/<owner>/system/backup`. Keep the original operation ID through pending responses. A committed receipt identifies a verified manifest, owner D1 table snapshot, private immutable R2 object copies and their hashes. Download the manifest and every listed part using the authenticated Admin controls. Save the release source SHA, configuration mapping without secrets and independent manifest checksum alongside the package. Protect these artifacts as school data.

A per-owner D1 snapshot is consistent within that database. Eight independently captured backups are **not** a cross-D1 transaction. For a suite cutover/recovery point, stop new admission and jobs under the approved maintenance procedure, resolve or fence in-flight operations, capture all owners and record source/destination receipts together. Keep all referenced historical Contacts/Deploy artifacts. Automatic audit/history deletion is disabled.

The implementation deliberately provides no live HTTP restore command. `v1/runtime/backup.mjs:restoreOwner` restores into an empty isolated owner D1 and private R2 bucket with the exact table/index/trigger/view schema. It verifies school-qualified object paths and scope, all source hashes, destination R2 readback and database rows before reporting `verified-owner-restore`. A failed partial restore remains an unusable isolated target; abandon/recreate it before another restore. Never restore over production data.

A verified owner restore returns `activationReady:false`. Prepared writes are fenced as aborted, their admissions are invalidated, and every formerly queued/leased provider job becomes uncertain because it might have sent after the snapshot. Held cross-owner pins remain until destination receipts/fenced aborts prove their outcome. Restore the complete suite, reconcile each original operation and provider identity, confirm current source heads and accepted facts, then exercise representative reads, protected writes and publication recovery before any activation. Do not convert an unknown outcome into fabricated success or blindly replay an old queue.

Local tests exercise fresh-store restoration, restart, original authority observation/snapshot recovery, committed receipt association and corrupt/missing/nonempty/scope negatives. A hosted Cloudflare restore rehearsal, browser-only restore automation and provider reconciliation rehearsal remain release gates; they have not been performed. Preserve F5 OPEN pending exact-head independent review of durable evidence and any required staging evidence. Official T1B-01/T1B-02 remain Not tested.

## REIGN archive, Wrapped recap and explicit cleanup

OVERLORD keeps the existing period-close action and adds a guided recovery flow. Closing a period retains its records and recap. Prepare the closed period's readable Excel, complete JSON recovery data including photographs, and a visual Wrapped HTML recap; export each part to the configured LORD Drive folder; and verify every part before requesting cleanup.

The cleanup preview names the exact eligible booking IDs, photographs and preserved records. The administrator must enter the displayed confirmation for that preview. Only completed/cancelled, fully reconciled records in the closed period are eligible. Active/future work, outstanding devices/accessories, unresolved incidents, active capability links and uncertain background work prevent relevant cleanup. Settings, inventory, reference lists, period summaries, security/operation receipts and archive evidence are retained.

Database removal and R2 removal are separate phases. A failed or interrupted photograph deletion stays `cleanup-pending` and resumes the original operation. Google recovery files are not deleted. Every resume verifies archive integrity and remaining references; unknown outcomes are not success. Google and Cloudflare cannot be atomically committed together, so independently deleting a verified Google archive after cleanup can still destroy that recovery copy.

The current archive bounds are 2,000 bookings, 12,000 rows per dependent table, 32 photographs with at most 4 MiB combined photo bytes, 8 MiB per recovery file and 30,000 workbook cells. Oversized periods retain all data and report the bound; they need a separately reviewed partitioned-export extension. These are engineering limits, not a claim that every school-year archive fits. No live archive, restore or deletion was performed for this change queue.

Telegram continues using the existing bot identity/token at an approved cutover. Its token and webhook secret belong in backend secret storage; they are absent from browser assets, generated source/configuration and downloadable packages. This implementation neither rotates the bot nor activates a v1 sender/webhook.

## Failure and rollback

For PR145, reverting the application does not undo completed imports, Google archives or confirmed REIGN cleanup. Keep the additive D1 tables and archive receipts. Resolve pending imports, batch source-pin acquisitions and cleanup phases before an approved code rollback; older code does not supply all new recovery paths. Preserve the verified Google package before any restoration decision. No automatic reverse migration or destructive rollback is supplied.

Before deployment, rollback is removal/rejection of this isolated branch/artifact; production sources and generated outputs are unchanged. During a future isolated deployment, keep incomplete services unrouted and integration ownership disabled; inspect the failed workflow step before retrying. D1 migrations and configured secrets may have completed before a later step fails, so never describe that workflow as an atomic suite deployment.

After a future live cutover, returning a route to old code does not reverse accepted facts, assignments, bookings, provider sends or accounting changes. Stop new writers/senders, preserve original receipts and uncertainty, choose an approved consistent recovery point, reconcile cross-owner references and external effects, and only then resume one active owner. No automatic destructive rollback or default authority records are supplied.
