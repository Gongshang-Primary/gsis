# Manual D1/R2 storage management

Global Admin Toolbox → Storage and prune. Owner request: 14 November 2026. This implementation is for review; no live deletion, migration or deployment has been performed.

## Inventory

Inspect each owning domain separately. D1 allocated bytes come from supported D1 result metadata (`size_after`); unsupported metrics display Unavailable. D1 rejects page-count/free-list PRAGMAs in Workers, so the interface does not fabricate free-page figures. Deleting rows can make pages reusable without shrinking the allocated database file. The screen does not run VACUUM or promise a billing reduction.

R2 reports object count and bytes for one bounded listing page (100 objects), split into backup copies and operational artifacts. Continue through pages explicitly. These are owner-bucket observations, not Cloudflare account billing totals or an atomic whole-bucket snapshot. Unknown-scope objects are counted without exposing their keys and cannot be pruned here.

## Allowed manual pruning

1. **Expired temporary previews** in Calendar and Layout. Up to 100 rows, already expired at the server-issued cutoff. Valid previews and pending operations block/limit the applicable cleanup. No other D1 table is a generic cleanup target.
2. **Abandoned attempt files within one completed backup**. The backup must have a committed `system.backup` receipt and matching owner/school manifest. Only recognised content-addressed attempt paths absent from that immutable manifest are eligible. The manifest, database snapshot and every referenced object copy remain protected. This removes failed/retried attempt debris, not valid backup history.

Preview returns exact IDs/keys, a digest and typed confirmation. It expires after five minutes. Confirmation reselects and checks the exact digest. D1 deletion and the cleanup journal commit atomically with authorization and audit. R2 candidates are recorded as pending; the operator explicitly finishes that recorded cleanup. Every selected key is checked again against the unchanged committed manifest, object identity and current authority. Missing keys on resume mean an earlier attempt already deleted them. Success is reported only after absence is verified and the journal is complete. No atomic transaction spans D1 and R2.

The durable journal allows a page/process restart to list and resume pending work. A failed/uncertain request must retain its operation ID or inspect the existing journal; do not infer success from HTTP acceptance alone. Competing same-operation requests replay their receipt. A changed manifest or object blocks completion. A known rejection may abort that transport operation; the confirmed cleanup plan remains pending for a fresh authorised resume.

## Protected data and larger cleanup

Never delete authority snapshots, Contacts history/catalogues, observations/F5 evidence, security audit, operation receipts, source pins, fencing/lease history, provider uncertainty, valid backups or operational artifacts through a generic rule. No age-based sweep or automatic retention deletion is introduced. D2 Drive retention remains an owner choice; manual Drive deletion is separate. D1 folder sharing is closed and owner-managed.

For large LORD operational cleanup, use the existing domain-owned REIGN archive/verify/confirm/finish flow. Calendar archives and Roster baseline maintenance retain their existing owner contracts. This Toolbox does not silently widen those controls or classify an unreferenced-looking staff/photo record as disposable. Longer-term valid-backup or evidence retention requires a separately approved policy and reference analysis.
