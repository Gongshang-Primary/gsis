## Material findings

1. **P1 — New-install instructions invoke initial administrator resolution before its Contacts dependency is configured. Status: resolved by `32f5cfd`, source rechecked.** `README.md:280–287` runs `setupVenues()` at step 3, but configures and republishes the Contacts signed source at step 5. `venues-backend/Code.gs::setupVenues` resolves every configured `VENUES_ADMIN_EMAILS` identity through live Contacts before it creates grants and before installing the minute trigger (`Code.gs:79–80`). `Sources.gs::venuesResolveActor_` calls the signed Contacts manifest/snapshot path, whose `backend/VenuesBridge.gs` verifier requires the bridge secret. Following the new-install order therefore fails after creating storage but before creating any usable administrator or job trigger. Later instructions do not explicitly rerun setup. **Smallest remedy:** configure/publish the source bridge prerequisites before running `setupVenues()`, and state that an interrupted setup must be rerun idempotently before health/trigger checks. This is a source-traced setup failure; no real installation was performed.

2. **P2 — Management short links load through the personal-list filter, excluding legitimate room managers. Status: resolved by `1648105` + `2a62106`, domain/browser checks passed.** `venues-viewport/public/app.js::boot` handles both `/b/<id>` and `/r/<id>` by switching to `mine` and calling `loadCurrent`; that read uses `mine:true`. `shared/venues.js::read` correctly restricts the occurrence list to historical requester/current owner in that mode, so a room owner or administrator following another person's booking approval link cannot obtain the booking. For timetable transfers the authorized transfer is returned, but `renderMine` filters it again to requester/original ad hoc owner, removing the room manager's review button. The `/r/` handler then silently finds nothing to click. **Executed evidence:** native Chromium with the real domain read function showed `/b/booking` reporting unavailable for its authorized room owner, even though the same domain's admin response included the booking; `/r/transfer` produced no dialog/button although the domain returned the transfer for that owner. **Smallest remedy:** read the selected record by ID under its proper live server permission check and route directly to its booking/transfer detail; keep personal-list filtering separate. Links must continue to grant no authority and must not mutate on GET.

3. **P2 — Closure management depends on whichever booking date was loaded previously. Status: resolved by `1648105` + `2a62106`, domain/browser checks passed.** `app.js::renderAdmin` renders `state.closures`, but `loadAdmin` never populates it and `shared/venues.js::read('admin')` omits closures. Only `loadBookings` fills that state, replacing it with the selected date range. After `saveClosure`, `editClosure` reloads `state.date` rather than the closure's range. A direct Administration entry therefore displays no existing closures, and a newly created future closure disappears from its management list. Administrators cannot reopen/deactivate such a closure through that view without first visiting its date elsewhere. **Executed evidence:** native Chromium loaded `?view=admin` with a real, authorized future closure in domain state; there was no edit control and the domain admin response's `closures` field was undefined. **Smallest remedy:** include the authorized closure list in the admin response and update it from admin loads and returned mutation deltas; do not couple management state to the public booking viewport's selected date.

4. **P2 — Repeating-booking preview treats unqueried reservation dates as available. Status: resolved by `2a62106`, native browser checks passed.** `app.js::previewBooking` checks every generated date against `state.occurrences`, but only the current day has necessarily been loaded by `loadCurrent`. It does not fetch the chosen date range or check booking coverage. The available-date selector consequently retains later dates that already contain held bookings. The server prevents double booking, but the required preview and explicit available-date choice give incorrect guidance and the whole selection fails only at submission. **Executed evidence:** the real-domain Chromium harness had a pending booking on 27 October; after loading 26 October and selecting a two-date recurrence, the 27 October preview displayed “Awaiting approval” rather than conflict, and no bookings read covered the selected range. **Smallest remedy:** load reservation/closure deltas for the selected range before constructing the preview, with a loading/error state and stale-response guard. Keep final server admission authoritative and all-or-nothing for the chosen dates.

## Structural and performance assessment

The implemented ownership split is useful: browser display/cache, verified Worker identity, signed source adapters, pure domain rules, and persistence/provider shells. The immutable occupancy cache validates compressed-byte digests and declared uncompressed length before activating a complete generation, keeps bookings independent, and retains the previous verified generation after refresh failure. Per-record revisions, durable receipt/nonce tables and one Sheets batch for booking/audit/outbox intent are coherent boundaries. The persistence diff writes changed contiguous row spans and keeps unchanged occupancy metadata separate from ordinary reservation counters. No new framework, type layer or file split is justified solely by the dense source formatting.

One deliberate performance ceiling remains: `venuesLoadState_` loads all 16 tables under the single Venues lock. The initial review identified redundant unchanged-Contacts and freshness loads (three full loads per warm read, four per warm booking). Commit `687257f` reuses the request's verified Contacts/source observation as a preparation hint, while the final locked transaction still checks the current Contacts key and the domain's current grants, record revisions, source fence and freshness. The piece-read path now also checks the Contacts key. Executed integration tests using the real source helpers establish **two full-state loads** and one live Contacts manifest check for either a warm read or warm booking, and reject concurrent Contacts deactivation, grant revocation and source fencing. This is a measured synthetic operation count, not production latency. Full-history partitioning is still a later option if actual school load requires it; it is not necessary to resolve this review.

The STAPLER change was inspected from draft capture through first send, acknowledgement, reload, copied-tab writes, migration and cleanup. It captures the full snapshot before enqueueing writes; waits for IndexedDB transaction completion and exact byte read-back; serializes writes; falls back to localStorage; gates Save before persistence; preserves the request ID and compact references in the same snapshot; forks on per-key conflicts; and deletes only the acknowledged matching record. Restore checks account/date/baseline plus current load/view before applying. No material defect was established in these inspected paths. Existing native-browser recovery tests were inspected; their claimed prior run is attributed to `v092-stapler-recovery-fix.md`, not rerun by this reviewer.
