# Deploy v1 owner

This isolated implementation follows accelerated specification v1.1 at `f39b671ac6da3f389c58345ce4f5c035f1cb3f65`, including frozen TV01–TV07, against product source `27fa498657965169b9d971a9caabc33c8b19bc69`. It imports pure existing workload, relief, planning-field and venue-group calculation modules. It does not import a production gateway or contact a production store.

`service.mjs` owns saved planning versions, scoped rows, editing leases, immutable publication pointers, operation receipts, audit projections and delivery intents. `model.mjs` implements the supported planning operations and calculation projection. `workbooks.mjs` owns exact workbook schemas, validation and replacement scopes. `exports.mjs` handles the readable continuity export. The gateway packages the existing Deploy frontend with v1 authentication, canonical workbook and publication adapters.

## Mutation and publication boundaries

New planning versions persist an explicit year, using the current Singapore calendar year as a visible default unless the caller provides another year. Publication rejects a missing or invalid year, and downstream Layout receives the immutable planning year. Each protected change has its original operation ID, canonical intent digest and fence. Final D1 transactions verify stored admission evidence, revision guards and editing lease fences, then write business changes, audit and receipts atomically. Disjoint rows can save independently; metadata, import and publication actions bind the relevant whole version. A changed value retains the caller's draft and requires review. Preview is an expiring actor-bound preparation artifact. Apply checks preview identity, saved base, Contacts dependency revisions, current authority and lease again.

Publish verifies the canonical payload in private R2 before preparing a durable publication. Venues verifies that preparation's exact operation and Core request binding before registering its source fence. The final Deploy transaction updates the pointer by CAS and writes immutable metadata, receipt and independent Contacts, Roster, Venues, Layout and Drive export intents. Contacts contributions are split into stable chunks of at most 64 fields, with aggregate delivery acknowledged only after every chunk is durable. Later consumer errors cannot undo publication. A matching retry returns the original receipt plus the current pointer; an unknown receipt does not imply no save.

Contacts owns permanent Staff IDs and every accepted personal fact. Its versioned catalogue projections populate the read-only HR Terms and Membership tables; catalogue flags never grant authority. Reporting edits re-read current accepted facts and protect explicit School Leader roots. The named ContactsDeploymentProjection binding exposes only current published assignments, raw workload values/quality and organisation references to Contacts; it omits planner notes and authority evidence. Name-only registration delegates to Contacts. Deploy edits/imports can propose only the approved contribution fields; contributions never become accepted authority. Calculation uses accepted observations, including exact revision/as-of evidence, and carries verified/estimated/unavailable quality. TV05 freezes the calculated cap basis, configured-cap flag and complete non-teaching reservation map together with saved subject classifications and explicitly declared non-teaching activities. Missing or incomplete reservations remain null; Roster computes effective five-day occupancy and cap verification separately. Historical envelopes lacking those inputs require manual republication for new capped decisions, not inferred defaults. Incomplete shared inputs cannot produce a verified shared average. Explicit EO evidence is required; labels and names do not grant authority.

Deploy's source occupancy projection is a **planning reference**, with `coverage: null` unless actual dated coverage exists in the owned document. Inspection of baseline `backend/DeployVenues.gs` found room/register references and publication windows, not a dated timetable. An empty planning projection does not mean venues are free. Used room references carry exact canonical venue revisions and are fenced against metadata changes during publication. Venues combines the current Deploy reference with verified Roster dated coverage, and blocks unknown coverage. This avoids fabricating timetable semantics.

Expired preparations become terminal only after D1 durably advances the operation fence and writes an aborted receipt. Scheduled recovery resolves pins from that receipt and reconciles the Venues source fence. Owner outages leave recovery pending. Pin expiry alone never proves safe release. Committed operation evidence is linked to Core's durable decision evidence; failed linking remains retryable independently of the business receipt.

## Delivery and operator status

Each consumer has an independent durable delivery result and original publication proof. Delayed adoption verifies the committed immutable publication; it does not reuse an expired user session to authorize new mutable work. Contacts delivery means proposals were received, not accepted. Retrying Contacts delivery retains the original publication identity. Audit display archiving changes only the administrator's display cutoff; immutable audit, publication and recovery evidence remains available.

Drive export requires `SEND_OWNER=v1`, `DEPLOY_DRIVE_FOLDER_ID` and an approved Google credential configuration supplied through the deployment path. It durably records a generated file ID and content digest before provider creation. A lost response remains uncertain; it is never blindly resent. Administrator reconciliation reads the exact provider file, checks its hash and commits the acknowledgement through current protected admission. CSV formula-like strings are escaped. New publications use distinct immutable files, preserving earlier good exports when a newer export fails. No live credentials or provider calls were used during development.

## Evidence and limits

Run with `TZ=Asia/Singapore`:

- `node tests/v1-product-deploy-workbooks.mjs`: exact workbook scope/negative cases, Span of Control reconciliation and TV01 numerical semantics.
- `node tests/v1-product-deploy-storage.mjs`: actual Miniflare Workers D1/R2 drafts, disjoint saves, stale lease rollback, atomic import, publication, original receipt retry/restart, dependency outage, fenced expiry recovery and payload integrity. Core/Contacts/Venues dependencies in this focused test are explicitly synthetic adapters.
- `node tests/v1-product-deploy-exports.mjs`: actual D1 restart with synthetic Drive response loss, durable generated identity before send, no ambiguous resend and verified readback. No provider is contacted.

The root integration suite supplies real local Worker service bindings and owner databases. Focused tests alone do not establish that integrated admission, durable F5 recovery, browser behaviour, production identity/provider settings or deployment work. Exact-head integration/build/regression results belong in the root delivery evidence. Runtime UAT and live provider/deployment checks remain **Not tested** unless independently performed and evidenced. There is no transaction across separate D1 databases; owner pins order protected changes against one destination commit, and asynchronous projections have separate outcomes.
